## Context

The current release workflow (`version.yml`) has a `create-release` job that runs `npx github:davegarvey/bubble` to generate AI release notes via the OpenAI API. This job is a single point of failure: if it fails (expired API key, npm outage, bubble error), the downstream `build-release` and `publish-crate` jobs never run, leaving the GitHub Release without binary assets and the crate unpublished.

The canonical release-please pattern generates the release body from the CHANGELOG entry that was already committed as part of the release PR. No AI, no external API needed. The CHANGELOG entry already exists on the merge commit — the gap is just plumbing it into the release body.

Instead of fetching the CHANGELOG entry from the merge commit at release time (which requires API calls or `git show` plumbing in the workflow), we can set the PR body to the changelog entry when the PR is created. The PR body then flows naturally into `gh release create --notes "${BODY}"` after merge — no extra step needed.

## Goals / Non-Goals

**Goals:**
- Add `--changelog-entry` flag to grubble that prints the latest entry from CHANGELOG.md
- Use the changelog entry as the release PR body at creation time
- Remove the `create-release` job and its bubble dependency
- Fix `build-release` and `publish-crate` to not depend on `create-release`, so asset failures never block the release pipeline
- Update docs to reflect the new flag and simplified workflow

**Non-Goals:**
- Changing the `--release-from-pr` output format
- Adding new GitHub API calls to grubble (the changelog is read from the local filesystem)
- Altering the CHANGELOG.md generation format itself
- Removing the existing `body` field from `--release-from-pr` output (it still works as a fallback)

## Decisions

### Decision 1: New CLI flag vs. shell extraction

**Choice:** Add `--changelog-entry` CLI flag to grubble.

**Alternatives considered:**
- **Shell regex in YAML** (`sed`, `awk`, `python3 -c`): rejected as untestable, fragile, and inconsistent with the project's philosophy of pushing logic into Rust
- **`git show $SHA:CHANGELOG.md | python3 ...` in the workflow**: same problem — regex embedded in shell string
- **Fetch via `gh api` in `--release-from-pr`**: adds API call for content that's already on disk, more surface area

**Rationale:** `--changelog-entry` is a simple pure-Rust function that reads a local file and extracts the first (latest) section. It follows the existing pattern of read-only flags like `--raw` and `--bump-type`. It's testable with unit tests, has no external dependencies, and integrates cleanly with the workflow.

### Decision 2: Set PR body at creation time vs. update release body after merge

**Choice:** Set the PR body to the changelog entry when the PR is created. The body then flows to `gh release create --notes "${BODY}"` naturally.

**Alternatives considered:**
- **Extract from merge commit at release time**: would need `git fetch origin $SHA --depth=1 && git show $SHA:CHANGELOG.md | ...` in the Release step. More moving parts, and the content changes between PR creation and release (the file on the merge commit is the authoritative version, but we already have it as the PR body).
- **Update release body after `gh release create`**: an extra API call (`gh release edit`).

**Rationale:** Setting the PR body at creation time is the simplest path. The PR body IS the changelog entry — it's set once, travels through the PR lifecycle, and is available as `body` in `--release-from-pr` output without any new code. The `gh release create --notes "${BODY}"` call already uses this field. No new fetch, no new API call.

### Decision 3: Remove `create-release` job vs. make it non-blocking

**Choice:** Remove the `create-release` job entirely.

**Alternatives considered:**
- **Keep `create-release` but make `build-release` not depend on it**: still pays the Node.js setup tax and API key maintenance. The bubble output was overwriting the release body anyway — the canonical pattern uses the CHANGELOG entry, not AI text.

**Rationale:** The `create-release` job served a single purpose: run bubble. With bubble removed, there's nothing left in the job. The CHANGELOG entry is already generated by `grubble --changelog` in the `Open or update release PR` step.

## Risks / Trade-offs

- **PR body size**: CHANGELOG entries can be long. GitHub PRs support multi-line bodies, and `gh release create --notes` handles them. No practical limit issue.
- **PR body contains markdown**: The changelog entry uses markdown formatting (headings, lists). The PR body and release body are rendered as markdown by GitHub — this is correct behavior.
- **`--changelog-entry` on a file without a changelog**: Returns empty string. The workflow falls back to the existing placeholder PR body. Non-breaking.
- **Existing PRs with old placeholder body**: The workflow checks `gh pr view` — if the PR already exists, it force-pushes the branch but doesn't update the body. This is acceptable because the release notes during development don't matter — the release body is what ships, and that's set at `gh release create` time. When a human merges, the `--release-from-pr` step reads `body` from the PR which still has the placeholder. To handle this, the Release step will also attempt to extract from the CHANGELOG at release time if the body is the old placeholder format. Alternatively, for simplicity, we accept that existing in-flight PRs show the old body — the fix applies to all new PRs.
